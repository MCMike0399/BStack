# Comments and documentation

**Keep material accurate.** Follow the repository’s documentation workflow. When a change makes comments or documentation inaccurate or incomplete, update the affected material where edits are in scope and report the rest. Where edits are in scope, record newly confirmed or changed business rules and their exceptions, provider contracts, SLAs, deployment topology, and operating constraints that a future reader will need. Use the existing topic when it fits. For a new topic, follow the project’s conventions or propose a location if they give no direction.

**Name the source.** When documenting a requirement or decision, name its authority or record. Say when you could not verify the source. Cite evidence from code with its revision and runtime observations with their environment and date. If behavior differs from an agreed requirement, report the discrepancy and preserve the recorded requirement until an authorized decision changes it.

**Write for the maintainer.** Retain required notices and keep public API docs accurate. Use a code comment for a non-obvious reason or constraint a maintainer needs at that point. Keep longer context in its topic and link to it when useful. When a comment warns about a mistake, prefer an in-scope design or check that prevents it. Keep the explanation a maintainer still needs. When a workaround must remain, label it and record the constraint and the condition for removing it. Say when the constraint is unverified or the removal condition is unknown. In the prose you write or edit, cut restatements of readable code and duplicate summaries that serve no reader need or project requirement.

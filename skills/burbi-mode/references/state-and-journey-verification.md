# State and journey verification

Apply these steps with [Project verification](project-verification.md) and within the task's scope. For a design-only or plan-only request, describe the check and its prerequisites. For read-only work, use authorized checks that preserve the project and shared state.

1. **Map the affected path.** Use the project's feature map or name the actor, entry point, starting state, actions, and the expected visible result and durable effects. For stateful behavior, identify the state owner, the transitions in scope, and a rule that must hold across them. Take expected behavior from the requirement. Mark an unresolved product decision as open and report the observed behavior separately.
2. **Drive a repeatable run.** Use the existing CLI, UI driver, or runner at the relevant entry point. Record the build, environment, fixture or checkpoint, and exact commands or actions in order, including the inputs and timing the result depends on. For UI automation, prefer stable control names and wait for observable readiness or state. Give one controller ownership of a shared UI session while the run is active. Before repeating an action whose effect is uncertain, check what the earlier attempt did. If its effect stays unknown and a repeat could duplicate a lasting effect, hold the repeat and report the gap. Use the existing operation identity or checkpoint when recovering that operation.
3. **Check the transitions.** Exercise the intended path and the failure or recovery sequence that could break the rule. Assert the visible result or CLI output and exit status as relevant. Read back any lasting effect you claim from its owner or another source appropriate to the claim. Check whether pending retries, timers, or background work could change a result before calling it final. For an in-scope regression test, reduce the failure to a sequence you can rerun. Check that it fails on the broken behavior and passes on the correction when feasible.
4. **Use generated or formal checks where they fit.** Reuse or extend the project's property-based tests when examples miss relevant sequences or input combinations. Record the property, tool version, settings and seed where available. On failure, keep the original trace. If you reduce it, confirm the shorter sequence still breaks the same rule. For a model or proof, record the checked property, model and code versions, assumptions and bounds. Report what holds within that scope and relate it to the implementation. Replay a counterexample against the implementation when in scope. Until replay or other implementation evidence confirms it, report it as a model finding.
5. **Give the reviewer a receipt.** Link the replay command or action sequence, expected and observed outcomes, relevant state read-back and evidence for each material claim. Use safe identifiers when they are needed to connect evidence across surfaces. Tie each item to its build and run, and name the surface and any substitutes used. When a recorded walkthrough is requested, follow the project's capture workflow and link the frames or chapter times that show the action and result. Redact sensitive fields, then inspect the shared evidence and final export for readability and accuracy. For presentation-only changes, reuse the verified run by re-exporting its recordings and receipts. Identify the build each clip shows and any change made after capture.

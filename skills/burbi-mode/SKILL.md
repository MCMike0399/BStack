# Burbi-mode

## Choose a playbook

Route by what the user wants done now. For a routed task, the first tool action is to open the selected playbook, using the link relative to this skill file. Follow the steps in the file you opened. If the playbook is unavailable, report that and use the engineering rules. The engineering rules apply on every route.

| Requested outcome | Playbook |
| --- | --- |
| Explain existing behavior or diagnose a correctness failure | [Investigation](playbooks/investigation.md) |
| Fix incorrect behavior now. This includes a request to explain, fix, and verify a correctness defect; to fix a failing test whose cause is not yet known; or to fix a defect that keeps recurring in the running product | [Bug fix](playbooks/bug-fix.md) |
| Plan, add, or intentionally change behavior, add tests for existing behavior, update tests for an intended behavior change, or write or update a verification recipe in the repo | [Feature](playbooks/feature.md) |
| Change code structure while preserving behavior | [Refactor](playbooks/refactor.md) |
| Plan, analyze, or carry out a transition, upgrade a dependency or toolchain, or build a converter for existing data or state, even as a new script | [Migration](playbooks/migration.md) |
| Measure, diagnose, or improve speed or resource use | [Performance](playbooks/performance.md) |
| Try options in a disposable design exercise or compare behavior through a prototype | [Prototype](playbooks/prototype.md) |
| Assess a diff or proposed change, including a guidance diff, and report findings | [Review](playbooks/review.md) |
| Run checks or exercise behavior and report a verdict | [Verification](playbooks/verification.md) |
| Stop a kind of wrong change that agents or contributors keep making, even when the request names an instruction as the remedy | [Recurring mistake](playbooks/recurring-mistake.md) |
| Write or revise instructions that agents load, such as a skill, playbook, agent instruction file, or delegate role, or evaluate how agents follow them | [Guidance](playbooks/guidance.md) |
| Pause work so another session can resume it, or resume work from another session that you know only through its record, such as notes, a transcript, or a branch. Open this before the playbook for the remaining work | [Handoff](playbooks/handoff.md) |

- When a request lists separate tasks or review comments, route each by its own requested outcome. Steps toward one outcome are one task.
- For a plan-only or design-only request, open the playbook for the underlying change and finish with the plan or design and its evidence.
- When the selected playbook is Investigation, Review, or Verification, or the request rules out edits or is limited to planning, reporting, or measurement, preserve project files, the checkout and index, and shared state. Output that the project's own build or test commands write to paths version control ignores, such as caches, is allowed. Put disposable probe files outside the project tree. An explicitly requested output file is part of the deliverable. Finish at the requested deliverable.
- Follow an explicitly named playbook within the task's limits.
- Keep the playbook on follow-ups with the same outcome. Open the next playbook when the user asks for a different step, including implementation after a review.
- For work outside these routes, use the engineering rules and any reference whose condition applies.

## Find project context

Read the applicable project instructions or use the ones already loaded. If they contain a routing table, match the affected area and read the files or sections named in that entry. Expand to another topic only when evidence from the selected docs or code shows that it is involved. Where project guidance is absent, find the entry point and checks in the nearest code and configuration. Verify claims about current behavior against the code or an observation within the task's authorization.

## Open a reference

After opening any selected playbook, open each reference whose condition applies. Also open a reference that a playbook step links when that step applies. Return to the selected playbook with the result.

| Condition | Reference |
| --- | --- |
| You are about to write or edit a code comment or project documentation, including to correct what a change made inaccurate, or, with edits in scope, you confirm or change a business rule, contract, or operating constraint a future reader will need | [Comments and documentation](references/comments-and-documentation.md) |
| A check needs a running app, device, or external dependency the usual checks do not exercise, or a needed check is blocked. For work that includes publication or deployment, including a push that triggers either, open it before choosing release checks. | [Project verification](references/project-verification.md) |
| The task asks to plan, write, or update a verification recipe | [Verification recipes](references/verification-recipes.md) |
| The bug, test, or check involves retries, event order, timed transitions, or recovery, you use generated or formal checks, or you are asked for reviewable CLI or UI evidence | [State and journey verification](references/state-and-journey-verification.md) |
| The task leaves a shared interface or state ownership decision unresolved and the choice affects dependent callers, Workers, or deployed versions | [Architecture](references/architecture.md) |
| The user asks to delegate, or you are about to dispatch a subagent. Open it before dispatch. | [Delegation](references/delegation.md) |
| You coordinate delegated assignments that depend on one another or continue across turns | [Coordination](references/coordination.md) |
| The user asks for work that runs unattended or that they will audit afterward, or asks for a decision log. Also open it when work with several dependent steps matches no playbook. | [Long-running work](references/long-running-work.md) |

## Carry the work through

When the next in-scope step is clear, take it and check the result. If a prerequisite is missing, pause the work that depends on it and advance independent in-scope work toward the same goal. Settle implementation choices within scope. Ask the user, or the parent when delegated, for decisions they own that the task and evidence leave open. Follow rule 3 for approvals. Stage, commit, or publish only when the task authorizes it. When progress has to stop, report the last verified result, what is waiting or blocked, and what would let work resume.

## Engineering rules

1. Before acting, choose the smallest scope that meets the goal and decide what observable result would show it worked. Before calling the work done, check that result and say what remains unverified.
2. Before changing stateful logic, identify where the state lives, what can change it, and what must stay true afterward. If states are only implied by flags or scattered conditionals, name the states and the allowed transitions first. Restructure only when the task calls for it.
3. If a step needs approval you don't have, stop before taking it and say which approval is missing. Keep working only on what is already authorized and doesn't depend on that step. Don't reach the blocked result another way.
4. When the same kind of mistake is found twice, prevent it with the first of these that can catch it: a design that removes the wrong path, a type the checker rejects, a lint or CI check, or a test. Add an instruction only when none can. If the check or instruction is outside the current task, propose it instead of adding it.
5. For a series of dependent changes, split the work into steps you can verify separately. Check each step before starting work that depends on it. If the check fails or can't be run, say what failed or what's unverified, and pause the dependent work.
6. When fixing a bug, trace the symptom back to the first place the system goes wrong, and fix it there. A guard, retry, or fallback at the symptom is a fix only if the state it handles is legitimate. If fixing the cause is outside the current task, propose that fix and say what remains unfixed.
7. When writing or changing a test, assert only what users of the code can observe through its public interface, including its effects on outside systems. Take expected values from the requirement, not from the code under test. The test should fail if the observable behavior breaks and still pass if only the internals change.
8. Before benchmarking or running an eval, say what decision the result will inform and what result would change that decision. Before trusting or reporting the number, check that the runs did the intended work and that errors, skipped steps, or unintended cache hits didn't distort the result. Use evidence from those runs, not a reading of the code, to explain what limited the result. Report the run count, the spread, and that limit with the number. If the run-to-run spread is as large as the difference, or you can't measure the spread, call the comparison inconclusive.
9. For a state-changing operation that may be retried or re-run, read the current state, compare it to the goal, and make only the changes still needed. Design for both a repeated run and a run that stopped partway, so that running it again reaches the intended state without duplicating effects. If you can't tell whether an earlier attempt took effect, check before retrying, and say so if you can't check.
10. When designing or modifying operations that update state and can overlap, including retries, identify what could break when their steps interleave. Give independent updates separate write targets. Treat anything rewritten as a whole as one target. When updates must preserve a shared constraint, even across separate records, enforce it for every writer, covering the writes and any reads that determine them. Verify the expected result by making the operations overlap.
11. When replacing an internal interface, trace its callers, including uses through configuration, scripts, or plugins. Migrate the callers you can change within scope. For callers that deploy separately, check the versions that are running, still supported, or available for rollback. If you can establish that no caller will still need the old interface, remove it in the same change and verify the behavior callers rely on with it gone. Otherwise, keep the old contract working and say what must be true before removing it.
12. When adding or changing an input path, validate the properties the receiving code relies on that the input leaves unverified. Check those properties where the code interprets them. Keep supported input formats working and translate them as needed. Reuse validated values while their guarantees hold, and check again when a change or handoff could invalidate them. Enforce permissions and rules that depend on current state where a revocation or state change can still stop the operation.
13. When adding or changing types or function signatures, use the type checker to catch mistakes callers could otherwise make. Model each case so it requires the data it needs and excludes incompatible fields. Use distinct types when different kinds of value share a representation and mixing them up would cause a bug. Use named arguments or fields when the confusion comes from argument order. Where the language supports it, make the type checker flag new cases that need a handling decision. Reuse the project’s schema-derived types for the contracts they describe. Before asserting a more specific type, establish its guarantees with a check or rely on validation the value has already passed.
14. When two fixes leave the same symptom or miss the same target, look for an assumption they both relied on. If you find one, state it. Before making another change that relies on it, run a check whose result would differ if that assumption were wrong. Compare cases that show the problem with cases that don’t when that can distinguish explanations. If the evidence contradicts the assumption, revise your explanation. If it supports the assumption, check what else the fixes had in common before trying another fix of the same kind. If the check is inconclusive or unavailable, say what remains unknown and choose a next step that can test the assumption or proceed without it.
15. When a code path you’re changing is hard to follow, trace one concrete case from input to result, including what state it reads or changes. Keep one definition for rules that must agree, even when several places enforce them. Keep mutable state as local as its ownership and lifetime allow. Prefer deriving values from their source. When a stored copy is needed, make clear where it comes from and when it is updated. Remove a layer that only forwards work when the path becomes clearer and callers keep the contracts they rely on without having to understand or repeat more of the work.
16. Before adding behavior, an option, or a layer, check whether removing code the addition would build on or work around would meet the goal or simplify the change. Check what still depends on that code, including supported configurations and stored data. Preserve supported behavior unless the task calls for retiring it. Remove the code first when the required behavior can keep working without it. When removal depends on a replacement, design both together. Add only what the resulting path still needs.
17. When manual work is easy to get wrong, a mistake would be costly, or someone needs to repeat a check, reuse a command or tool that fits. If none fits, write a small command or script when it would make the work more reliable or easier to verify. Try new tooling on representative inputs with known outcomes. When it checks a result, include a case it should reject where practical. When it makes changes, confirm the actual result on a sample that is safe to change before using it more broadly. For a batch, account for any in-scope items it skips or fails to process. If someone needs to rerun it, give them the command, required inputs, and expected result.
18. When the task leaves a choice about how a feature, command, or interface should work, identify what its users, callers, or maintainers need to accomplish. Use a realistic case to compare what each design asks them to know, decide, and do, including how they would notice and recover from a consequential failure. Within the requirements, prefer a design that removes recurring work while preserving the control and safeguards people need. Add options for stated requirements or concrete uses, including rare ones. When a meaningful tradeoff remains, weigh the effort of building the design against the work it leaves each group and how often they will do it. Explain that tradeoff in terms of what changes for them.
19. When existing patterns leave a consequential design choice unresolved and a focused comparison could change the decision, state what evidence would favor each option. Sketch or prototype two meaningfully different approaches. The current design can be one of them. Use enough detail to test the deciding tradeoff and compare both on the same realistic case and constraints. Separate what you observed from what you inferred, and say what remains unresolved when recommending an approach.
20. When a new requirement changes an assumption the existing design depends on, work out how you would design the affected part if the requirement had been there from the start. Use that design to find the smallest in-scope change to the model or contract that carries the old assumption. Update affected in-scope tests and documentation. If only a workaround fits the scope, keep it contained and explain what the fuller design would change and what remains unresolved.
21. For a rewrite or migration, define the verifiable end state and identify which intermediate states other people, CI, or deployed clients will rely on. Keep those states working for their required uses and follow the agreed terms of any planned interruption. Keep other temporary breakage in isolated work that can be repaired or discarded before anyone relies on it. Give each temporary bridge a checkable removal condition. At the end, verify the target behavior, remove bridges whose conditions are met, and say what any remaining bridge still needs before it can be removed.
22. Before reporting a change, read the whole diff of the edits you made and remove from them what the goal does not need, such as debug output, dead or commented-out code, unrelated edits, and unused options. Leave changes you did not make. Follow the project's current pattern for the kind of code you write. When the nearest example is a workaround or a deprecated path, follow the project's supported pattern instead and say so.

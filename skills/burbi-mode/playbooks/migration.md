# Migration

1. Define the old state and an observable end state. Trace who can read or write both, including callers that deploy separately and versions available for rollback. Name what must work during the transition and which state is authoritative at each phase.
2. Choose the smallest verifiable sequence. For each dependent step, name its success check and what happens if it stops partway. Define when temporary compatibility can be retired. For a plan-only or design-only request, finish by reporting the sequence and evidence still needed.
3. Prepare any conversion tooling the task asks for. Rehearse the transition on disposable data that represents the supported old state. If representative data is unavailable, record that gap. Check reruns and partial runs where interruption is possible. When old and new writers may coexist, verify what they must enforce together across the versions that will actually run.
4. Before applying the transition to its intended target, confirm the actual target is authorized and how to recover if the step fails. If either is unclear, finish at the last verified phase and report the blocker. Carry out authorized steps as their prerequisites pass. Verify through the real readers and writers. Report the phase reached, the evidence, and what must happen before retiring old paths.

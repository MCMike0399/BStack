# Recurring mistake

1. Gather instances of the mistake from the user's report and, within scope, from review comments, reverts, commit history, and agent instructions. Group them into classes. Treat a class as recurring once it has two instances or the user reports that it recurs. For each class, find what in the nearby code made the wrong change look right, such as an example to copy, a workaround, a deprecated path, or a missing check.
2. On this route, adding a check or test that prevents the class is part of the task, unless the request rules out edits or says to apply only the remedy it names. A redesign of shared code or a fix for a different defect is in scope only when the request asks for it. For each class, choose the first of these levels that can prevent it within that scope without blocking supported uses.
   1. Remove the wrong path from the design, for example by giving the state one owner, leaving one supported way to do the task, or deleting the code that gets copied.
   2. Make the type checker reject the mistake.
   3. Add a lint, CI, or script check whose message names what to use instead. When existing code has instances the task does not fix, record them as a baseline the check skips, fail only new ones, and report the remaining cleanup.
   4. Add a test of the observable behavior.
   5. Write an instruction, only for a judgment call that no check can decide, following the [Guidance](guidance.md) playbook.

   When an earlier level would prevent the class but is outside that scope, propose it. When the request names an instruction as the remedy, also add that instruction, in one sentence, to the file the request names, or to the project's agent instruction file when it names none. Name the check that enforces it when you added one.
3. Start with the most frequent class. Keep each class in its own change, and its own commit when the task authorizes commits. Show that each new check fails on a real past instance or a faithful reproduction of one, and passes on the correct form. Reproduce the past instance in a disposable copy outside the project tree. Run it the way the project's local checks and CI run it. If a new check also fails on current code because of a different defect, narrow the new check to the class so that it passes on current code and still fails on the past instance. Leave existing checks for other behavior unchanged. If it cannot be narrowed, keep it out of the project's default check run, report the defect and the command that runs the check, leave the fix to a separate Bug fix unless the request asks for it, and report the class as not yet enforced. A suppression that lets a new instance pass the check needs the user's approval. Without it, propose the suppression. With it, record next to the suppressed code the reason, who approved it, and the condition for removing it.
4. When the project's agent instructions already state a rule that a new check now fully enforces, shorten that rule to a pointer to the check. When the request does not ask for edits to those instructions, propose that edit instead. Keep an instruction the request asked for. Add no other instruction for a class a check enforces.
5. Report each class with its evidence, the level chosen, why each earlier level did not fit, the proof that the check rejects the mistake, and any class left unaddressed.

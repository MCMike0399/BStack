# Worker and Advisor foundations for BStack

This research proposes two roles inside the existing Burbi-mode playbooks. A Worker returns a checked deliverable from an assigned workspace. An Advisor challenges a decision or reviews a fixed artifact. The invoking agent decides when either role helps and owns the final result.

## What the sources support

Lauren Tan’s CODE 2026 talk puts codebase design, static analysis, and repeatable verification ahead of prose. She shows how agents can exercise real behavior and produce artifacts a reviewer can inspect. Her release automation comes after those checks are established. For BStack, the implication is to test what a delegate can change and what its result proves before adding unattended orchestration. ## Proposed roles

| Role | Brief | Capabilities | Return |
| --- | --- | --- | --- |
| **Worker** | One task, the base revision or input snapshot, relevant paths, observable acceptance check, writable scope, and expected artifact. | Work in an isolated checkout or scratch directory. Read the governing project instructions and relevant playbook. Edit the assigned output and run the checks available within the task’s authorization. | The patch or artifact, what changed, the exact check and observed result, and any unresolved limit or blocker. |
| **Advisor** | One question to challenge, or a fixed proposal or diff to review. Supply the user's intent, applicable standards, evidence, and any known verification gaps. | Start with supplied evidence and no tools. Where a review needs more context, provide a read-only view of the selected snapshot. Have the parent or a Worker reproduce findings that require execution. | A recommendation or actionable findings with affected behavior, source or reproduction, impact, and unresolved questions. Tie a review conclusion to the snapshot examined. |

Use a Worker for a separable task whose result the parent can check. Keep a coupled change with one owner, and do small edits inline when a handoff would cost more than the work. Use an Advisor when a second perspective could change a decision, expose a material failure, or check a change the user asked to review. An Advisor examining a change starts fresh against a fixed snapshot. A consultation can keep its context while the question stays the same.

The invoking agent owns the playbook, task boundaries, and integration. It gives each delegate only the context and permissions the assignment needs, checks the actual output, resolves findings against the evidence, and runs the acceptance check on the integrated result. Keep delegation one level deep at first. Publication, deployment, changes to shared state, and other external actions follow the original task’s authorization and stay with the parent. An unavailable model, timeout, or incomplete review leaves a coverage gap. A material change to the reviewed behavior calls for a fresh review on that artifact. ## What Pi can support now

Pi’s official subagent example launches a separate Pi process, takes an explicit working directory and model, applies a configured tool list, and returns JSON events. Start with one invocation at a time and an explicit role brief. Keep the Worker and Advisor instructions portable and use Pi as the first adapter. DeepSeek V4.1 Flash for the Worker and Fable 5.2 at medium effort for the Advisor match the providers already used in BStack. Record the model and effort the run actually used when the runner exposes them. [Pi subagent example](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/examples/extensions/subagent/index.ts)

I checked Pi 1.5.0 on Macintosh using a temporary RPC startup observer. With automatic extensions and MCP disabled, `--no-tools` yielded zero active tools. `--tools read,grep,find,ls` yielded exactly those four inspection tools. Adding `edit,write` yielded exactly those six tools for file edits. The observer used `pi.getActiveTools()`. This checked startup configuration without a model request. [Pi tool API](https://docs.pi.dev/latest/extensions#pigetactivetools--pigetalltools--pisetactivetoolsnames)

Use a worktree or separate copy to keep the Worker’s edits away from the parent’s working files. A worktree shares repository refs and config, and Pi tools run with the process’s permissions. For the first synthetic trial, use a separate copy with file tools and have the parent run the acceptance command, or expose a specific approved check. Use filesystem and process isolation when the assignment needs an enforced boundary. A tool list and workspace path establish different properties, so verify both before relying on them. [Pi safety overview](https://docs.pi.dev/latest#work-safely) · [Pi isolation guide](https://docs.pi.dev/latest/containerization)

### Dispatch behavior from the upstream implementations

- **Build a standalone brief.** PStack configures models by assignment and gives each Worker its own output, exact starting inputs, and a checkable finish condition. Pi’s example starts a fresh child with its own working directory and appends that agent’s prompt explicitly. In BStack, the parent supplies the core, the exact Burbi-mode rules, the assigned role, and the selected playbook when the role needs it. Project files and Advisor evidence stay scoped to the brief. [PStack setup](https://github.com/cursor/plugins/blob/main/pstack/skills/setup-pstack/SKILL.md) · [PStack Swarm](https://github.com/cursor/plugins/blob/main/pstack/skills/swarm/SKILL.md) · [Pi child launch](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/examples/extensions/subagent/index.ts)
- **Set child tools explicitly.** Pi’s example emits `--tools` only for a nonempty list. An empty list leaves the child on its defaults, which ordinarily include shell and editing. Explicit `--no-tools` is the appropriate Pi setting for evidence-only work. A Pi Worker uses a named file-tool list with automatic extensions and MCP disabled. gstack’s external review supplies its evidence up front and opens a fresh tool-free review, which fits the Fable Advisor. [Pi child arguments](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/examples/extensions/subagent/index.ts) · [Pi tool flags](https://docs.pi.dev/latest/cli#tools) · [gstack external review](https://github.com/garrytan/gstack/blob/main/docs/skills.md#claude-code)
- **Constrain the actual file operations.** Pi’s `tool_call` hook can block a call before execution. Native file tools resolve aliases and normalize paths, so validation needs to cover the final path the tool uses. Apply the read and write rules to a disposable copy and compare its files with the assigned inputs before returning changes. CWD gives the child a starting directory. Filesystem isolation requires an additional control. [Pi tool-call hook](https://docs.pi.dev/latest/extensions#tool_call) · [Pi path resolution](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/tools/path-utils.ts) · [Pi security model](https://docs.pi.dev/latest#work-safely)
- **Bind the returned evidence to the exact artifact.** Pi’s example handles cancellation, process failures, and failed assistant runs. tstack pins the artifact before review and checks findings before acting on them. BStack should return a dispatch status, the model observed, the input identity, and the artifact or findings. The parent verifies any Worker output and treats an unavailable or incomplete Advisor run as a coverage gap. [Pi process outcomes](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/examples/extensions/subagent/index.ts) · [tstack Sol Loop](https://github.com/t3dotgg/tstack/blob/main/skills/sol-loop/SKILL.md)

## First verification case

Run one Worker and one Advisor on the existing synthetic export-worker fixture. The Worker fixes duplicate output on retry in its own workspace and returns a patch and any available evidence. The parent runs the replay against the base and the patch. Include distinct IDs in the check so a patch that drops other exports cannot pass. Give the Advisor a fixed snapshot with a seeded regression and check that it identifies the affected behavior with evidence. Have the parent inspect the diff, apply only the intended patch, and rerun the verification on the integrated result.

Inspect the tool trace and file and Git state to verify that the Worker used its own workspace, the Advisor had no write capability, and the parent’s changes remained intact until integration. Exercise an incomplete Advisor result and a candidate that changes after review. Both cases should preserve the distinction between what was verified and what remains open. ## Pilot result

Two Fable 5.2 medium-effort reviews refined the [Worker](../skills/burbi-mode/roles/worker.md) and [Advisor](../skills/burbi-mode/roles/advisor.md) contracts. A Worker stops work that depends on a mismatched base and ties checks to the final edit. An Advisor identifies the reviewed snapshot, reports gaps as incomplete, and returns suggestions for the parent to evaluate.

The live macOS pilot ran a Pi Worker on DeepSeek V4.1 Flash in a disposable copy. Its sandbox denied reads and writes to the parent fixture and writes to the acceptance check. The Worker changed only `export_worker.py`. The parent verified retry deduplication and preservation of distinct IDs before applying the patch to its own fixture, then reran both checks.

Two fresh Fable Advisor sessions reviewed the Worker patch and a separate seeded regression. The tool inventory showed no workspace tools. Fable proposed replaying `job-17`, `job-18`, `job-17` against the seeded change. The independent replay confirmed that it dropped `job-18`. Local checks also rejected a mismatched Worker base before dispatch and withheld review coverage for incomplete results or a changed snapshot. ## How PStack combines skills, playbooks, and subagents

**Architect is a design skill.** The agent running it traces the affected systems, sketches two possible shapes for types, signatures, and modules, and chooses the shape with explicit state ownership and less work for callers. For a large or contested design it calls Arena, which gives parallel candidates the same brief and separate outputs. The caller compares and verifies the result. [Architect skill](https://github.com/cursor/plugins/blob/main/pstack/skills/architect/SKILL.md) · [Arena skill](https://github.com/cursor/plugins/blob/main/pstack/skills/arena/SKILL.md)

**Refactoring is a playbook owned by the invoking chat.** It captures existing behavior before moving code and calls Architect when the target shape crosses a function boundary. It delegates the mechanical edits with specific paths, symbols, and behavior to preserve. The invoking chat checks equivalence on the real surface. Larger cross-cutting structural work goes through Figure It Out. [Refactoring playbook](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/refactoring.md) · [Poteto-mode subagents](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#subagents)

**The repository separates agent definitions from model choice.** It ships `poteto-agent` for direct playbook delegation and `comment-sicko` for scoped comment cleanup and reshape findings. The parent gives delegates the Worker instructions and gives `poteto-agent` the Poteto-mode path. The `feature, refactoring` line written by Setup PStack selects a model for that assignment, with `claude-opus-5-5-xhigh-fast` as the default. Current setup identifies `architect runners` as a retired configuration key. `inherit-parent` and `auto` use a generic agent with the parent model. Routed workflow skills choose their own launch behavior. [Agent definitions](https://github.com/cursor/plugins/tree/main/pstack/agents) · [Poteto agent](https://github.com/cursor/plugins/blob/main/pstack/agents/poteto-agent.md) · [No Comments](https://github.com/cursor/plugins/blob/main/pstack/skills/no-comments/SKILL.md) · [Setup PStack](https://github.com/cursor/plugins/blob/main/pstack/skills/setup-pstack/SKILL.md)

**The talk explains why the evidence comes first.** Tan describes designing out repeated errors, catching the rest with deterministic checks, and letting agents exercise the real system before expanding automation. For BStack, this supports an optional design step followed by a bounded Worker brief, with independent advice when a choice benefits from it. ## Round three design recommendation

Fable 5.2 at medium effort reviewed the distinction and the migration team mapping. A role describes the delegate’s responsibility. A profile selects tools for that responsibility, within the grant for the specific assignment. A seat owns a named project responsibility. The parent uses playbooks to sequence work and skills to carry out individual steps. A model setting selects the model for an assignment without changing its authority.

Use an architecture step where a shared interface or state ownership needs a decision before dependent work. Trace callers and compare materially different shapes against ownership, caller burden, and the evidence for the tradeoff. A Worker may draft the design or build a scoped prototype. An Advisor can independently challenge it. If the decision depends on behavior nobody has observed, run a focused check or prototype. Parallel candidates are useful when a comparison actually needs separate artifacts. For a design-only request, return the design and evidence at that point.

Keep Refactor focused on preserving observed behavior. Record the baseline before editing and verify the result on the same surface afterward. Use Migration to coordinate old and new callers when both will run during the transition. For the Lambda team, ORCH resolves shared design decisions within its scope before MAIN and NET start dependent slices. REVIEW reads the exact revision, and OWNER retains production approval and execution. A separate Verifier seat is a candidate when independent checks recur across packets and need a distinct grant or continuity of evidence.

# Agent team workflow research

The Playdate team got useful autonomy by giving each worker a driver, keeping one integration owner for shared files, and routing evidence and blockers directly between seats. A fresh example ran from a worker's blocked checkpoint to an integration commit in minutes. BStack can exercise that loop in Markdown with its existing Worker and Advisor roles.

### Where the team lost time

The November 13 archive shows that a private bundle kept B moving without publishing, but an unpushed stretch of work and a runtime save were later lost. The bots switched to branch checkpoints after the owner's authorization. A partial proof survived because the reports carried the last recoverable SHA and save hash. The archive also shows routines that checked progress and usage, parked work near the agreed quota, and were resumed after an explicit owner request. A timer can trigger a review, and the review should act on a changed tip, a stalled lane, or a real dependency. Repeated video-only work, missing approvals, and relaying the same status all consume the same budget. See BlueBot archive 84, 125, 134–135, RedBot archive 145 and 262, and BlueBot live 295 and 302.

## Lauren Tan’s autonomy guidance

**The closest public prose is Tan's Engineering Lead Bot profile.** Its opening instruction is “own the loop (decompose, run, chase, report).” The profile asks the bot to follow work through merge, explicit abandonment, or user takeover. It reserves messages to the human for a blocker they can resolve, a merge-ready PR, or a result, and batches ordinary updates. It prefers a follow-up to the existing Cloud Agent or Project when that worker's context will help. Tan's dr eggbot profile adds “Bias to act once the job is clear” and gives coding bots one verifiable job. The two marketplace pages publish author-attributed Bot memories. I found no public Grok Bot platform system prompt in these sources. [Engineering Lead](https://x.ai/bot/marketplace/bots/engineering-lead) · [dr eggbot](https://x.ai/bot/marketplace/bots/dr-eggbot-v2)

**PStack supplies reusable execution language.** Autonomous run opens with “You own the exit condition. Define done, then drive to it without stopping.” It defines a checkable outcome, verifies each iteration, changes approach on a plateau, and surfaces a genuine dead end. Never Block on the Human encourages routine reversible work to advance while preserving the human's decisions and confirmations. Session pickup checks the actual inherited state and recovers the next step from the prior trail. [Autonomous run](https://github.com/cursor/plugins/blob/0b46ec399d55f2829e88822998f53b84944837d3/pstack/skills/poteto-mode/playbooks/autonomous-run.md) · [Never Block on the Human](https://github.com/cursor/plugins/blob/0b46ec399d55f2829e88822998f53b84944837d3/pstack/skills/principle-never-block-on-the-human/SKILL.md) · [Session pickup](https://github.com/cursor/plugins/blob/0b46ec399d55f2829e88822998f53b84944837d3/pstack/skills/poteto-mode/playbooks/session-pickup.md)

Its Worker guidance says “Make any choice you can undo, then say what you chose and why.” It also charges the worker with meeting the stated bar and keeping evidence reviewable. Poteto Mode starts fresh by default and resumes a delegate that holds state expensive to move, such as a checkout or running process. ## Grok Bot and Cursor delegation

Grok Bot gives a named Bot its own conversation and durable working context. A Bot can send an asynchronous request to a peer, wake that peer, and receive a reply. Group chats support visible coordination, and private handoffs appear in the Bots' own chats. The product guidance assigns one owner per stage and names the point where a person must decide. [Create and manage Bots](https://docs.x.ai/grok-bot/bots) · [Message and collaborate](https://docs.x.ai/grok-bot/chat-and-collaboration)

The coding handoff is built into Grok Bot. When the Cursor Cloud Agent finishes, the Bot copies the files cited in the final report and can attach them to its reply. Scroll back to the Cloud Agent card for its run link, optional PR, and attached files. Cloud Agent return files are absent from the Bot's Library. Grok Bot's documentation recommends evidence with direct sources, timestamps, and a record of what the Bot could verify. [How Grok Bot works](https://docs.x.ai/grok-bot/how-grok-bot-works) · [Files and results](https://docs.x.ai/grok-bot/files-and-results#results-from-cloud-agents)

## Grok Build source and patterns

xAI released the actual Grok Build Rust harness and terminal UI under Apache-2.0 in July 2026. The public repository contains the agent loop, prompt assembly, tool dispatch, and extension loading. It documents the Build CLI. The hosted Grok Bot product has separate collaboration and deployment documentation. The source observations below are pinned to the inspected commit, `2bdd1d6`. [xAI announcement](https://x.ai/news/grok-build-open-source) · [Grok Build source](https://github.com/xai-org/grok-build/tree/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8)

- **A role can be a brief without new permissions.** Build runs a child with independent context, a session-level tool configuration, and an optional persona for behavioral instructions and input/output expectations. Background spawn returns an ID to retrieve output later. A subsequent spawn can resume a completed child. [Grok Build subagents and personas](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-pager/docs/user-guide/16-subagents.md)
- **Addressed messages have operational meaning.** Build's optional local subagent messaging supports steering at a safe point, queuing a later turn, and urgent interruption of a wait. An eligible inactive child can wake on receipt. Pair and per-attempt limits bound child sends, and the transcript records send outcomes. These mechanics are a source reference for future Rakazo behavior. [Grok Build subagent messaging](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-pager/docs/user-guide/16-subagents.md#sending-messages-to-subagents)
- **Record which workspace the delegate actually got.** Build's inspected worktree code preserves working-tree changes when creating child worktrees. It falls back to the shared workspace if worktree creation fails. For a BStack experiment that requires isolated writes, check the actual checkout and starting revision before two delegates start editing. [Build worktree creation](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/agent/subagent/handle_request.rs#L675-L736)
- **Exercise changed behavior.** Build's planning prompt for web work requests interaction with the changed flow, related state, and edge cases, followed by another check after a fix. It asks the agent to identify what it could verify with a substitute when browser access is missing. The equivalent for a project with a simulator would be a defined input sequence and evidence of the resulting state. ## Cursor run records

Cursor's public beta v1 API returns an agent ID and an initial run ID when it accepts a task. A caller can specify a repository starting ref and request a PR. Later calls can steer the active run or send another prompt to the same agent. The run endpoint reports lifecycle state, timestamps, and the final reply, with the current pushed branch and PR when available. The API distinguishes a run waiting for background work from finished, error, cancelled, and expired runs. The CLI also supports handing its current conversation to the cloud. [Create an agent](https://cursor.com/docs/cloud-agent/api/endpoints#create-an-agent) · [Send a follow-up or steer](https://cursor.com/docs/cloud-agent/api/endpoints#send-a-follow-up-or-steer) · [Get a run](https://cursor.com/docs/cloud-agent/api/endpoints#get-a-run) · [CLI cloud handoff](https://cursor.com/docs/cli/using#cloud-agent-handoff)

The branch and artifact listing belongs to the durable agent, even when the agent has several runs. Artifact downloads use expiring URLs. For a reviewable handoff, record the run ID, exact checked commit, and stable artifact reference with the validation command or interaction and its outcome. A terminal run state describes the provider's lifecycle. The acceptance decision comes from the reported checks and the receiving agent's inspection of the result. [Run record](https://cursor.com/docs/cloud-agent/api/endpoints#get-a-run) · [Artifact listing and download](https://cursor.com/docs/cloud-agent/api/endpoints#artifacts)

## How this builds on Rakazo

The custom Rakazo fork already used the November 13 archive as input. At the inspected `65cd367b5`, its notes and implementation show a Worker with its own rounds and optional repository workspace, an explicit `continue` / `complete` / `blocked` report, and a wake to the driver at the end of a round. Peer replies can steer a running requester or wake it later, with hop limits to bound exchanges. The Advisor is a separate consultation that returns analysis to the invoking bot. These are source-level observations of the local fork. This research did not exercise the live Rakazo service. Local sources include `burbuja/collaboration-design.md`, `packages/adapters/src/worker-driver-tools.ts`, `worker-report.ts`, `worker-rounds.ts`, `messaging/bot-messages.ts`, and `pi-runtime-advisor.ts`.

The November 19 evidence points to an improvement above those primitives. Bind a report to its checked base, candidate revision, and evidence. Give a blocked report a responsible recipient and a specific resume condition. When that owner resolves it, pass the verified revision back to the driver so it can resume the existing worker from its durable checkpoint. Keep the worker's lifecycle, the review verdict, and the integration decision visible as separate facts. A scheduled check can surface missing replies or stalled checkpoints without taking a decision away from the owner.

## BStack guidance and proposed experiment

Burbi-mode's [Carry the work through](../skills/burbi-mode/SKILL.md#carry-the-work-through) guidance adapts PStack's bias to act on the next in-scope step. The [Coordination reference](../skills/burbi-mode/references/coordination.md) applies Lauren's lead-bot loop to dependent or continuing delegation with the existing [Worker](../skills/burbi-mode/roles/worker.md) and [Advisor](../skills/burbi-mode/roles/advisor.md). The choice to name a blocker owner and specify a resume condition comes directly from the Playdate handoff. Recorded checkpoints and checks let the parent recover from an interruption with evidence. For the Lambda migration example, ORCH would coordinate and route, MAIN and NET would own distinct work, REVIEW would check the evidence, and OWNER would retain the production decision.

1. **Launch.** Record deliverable, driver, base revision, workspace, writable paths, dependencies, acceptance checks, and publication authority. Check the actual starting state before parallel edits.
2. **Return.** Record outcome, base and candidate, what ran and what it showed, durable artifact references, and known gaps. On a blocker, name the next owner, dependency, last good checkpoint, and condition for resuming.
3. **Route.** Send an addressed handoff with a task identifier and the evidence needed for the next action. Continue independent work while waiting. If a new tip makes a verdict stale, qualify it and compare on the new tip before applying it.
4. **Integrate and confirm.** The integration owner compares baseline and candidate under comparable conditions and records the resulting tip. The worker resumes the same assignment after the dependency lands and supplies the acceptance evidence. The human still owns any action reserved for their approval.

Start with a Pi + DeepSeek V4.1 Flash sandbox task using two Worker lanes and an independent Advisor. Seed one shared-file blocker and one stale or incomplete proof. Run the same task against current Burbi Mode and with the proposed reference supplied. Hold the base, model, task, and tool scope fixed. Compare whether the team routes the blocker once, preserves a resumable checkpoint, catches the proof gap, and verifies the integrated tree. Record manual nudges, repeated checks, and elapsed time. Advance the reference into a playbook only if the coordination behavior repeats and improves the outcome.

An initial Pi + DeepSeek Flash smoke check missed the Verification-first route on the first draft. With the revised text, the ordinary task opened Verification first and left Coordination unopened. The prior skill also opened Verification first in one comparison run. In a separate read-only simulation of a dependent handoff, Pi opened Verification first, loaded Coordination, and ran the independent export check. The check contradicted a simulated Worker’s unverified pass. Pi left the approval-gated importer pending, reported the last checkpoint, and preserved the fixture files. The simulation exercised routing and evidence handling in one turn. Live worker messaging, wakeups, and comparative effects on autonomy remain to be measured.

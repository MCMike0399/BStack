# Documentation and comments research

## Public sources

### Lauren Tan and PStack

In *All Code Is Slop (Except Mine)*, Tan describes agents adding timers around a mismatch between VS Code’s imperative APIs and React’s declarative model. The agents explained why each timer was needed, and later agents copied the pattern. Tan describes a strict comment policy on her team and a move toward APIs, architecture, and lint checks that make the supported approach clear. Her example concerns what happens when prose makes a workaround look like an accepted pattern. The same talk shows her team using feature maps to record how users reach behavior that agents need to verify. [AI Engineer CODE talk and timestamped transcript](https://ai.engineer/code/2026/talks/lauren-tan)

PStack’s comment reviewer protects legal headers, public API documentation, verified outside constraints, and reference links that explain constraints code cannot express. It identifies confusing code owned by the project for a separate fix. The parent checks the reviewer’s findings against the named code and holds changes to the requested scope. PStack’s `/correct` skill handles recurring mistakes by preferring a design that eliminates them, then executable constraints and tests. A new check should reject a real past mistake. Its technical-writing skill gives explanations a legitimate purpose when they record a bounded decision, constraint, history, or alternative. ### What other stacks keep

**Matt Pocock’s domain modeling** captures settled terms in a glossary, checks disagreements against code, and uses concrete scenarios to resolve ambiguous terms. It offers an architecture decision record for a hard-to-reverse choice that would surprise a later reader and came from a genuine tradeoff. Files appear as terms and decisions earn them. The current skill uses `GLOSSARY.md` and `GLOSSARY-MAP.md`. The older names were `CONTEXT.md` and `CONTEXT-MAP.md`. BStack can borrow the threshold while respecting each repo’s established destinations. [Domain-modeling skill](https://github.com/mattpocock/skills/blob/abeeaf95660ba9e8b7c753eb38f441ca707a8823/skills/engineering/domain-modeling/SKILL.md) · [Domain-modeling guide](https://github.com/mattpocock/skills/blob/abeeaf95660ba9e8b7c753eb38f441ca707a8823/docs/engineering/domain-modeling.md)

**GStack’s release documentation audit** compares the candidate diff with the source needed to verify changed contracts and the project’s relevant authored docs. It corrects factual drift in an existing destination, records missing coverage for follow-up, and preserves a reporting path for read-only audits. Documentation is discoverable through the project’s guide or index. This supports checking affected pages when a change makes them inaccurate. [Documentation release skill](https://github.com/garrytan/gstack/blob/858679423cc4778f9961d4aaf3c061a9368985ec/document-release/SKILL.md) · [Audit scope and discovery](https://github.com/garrytan/gstack/blob/858679423cc4778f9961d4aaf3c061a9368985ec/document-release/sections/audit-scope.md) · [Per-file audit](https://github.com/garrytan/gstack/blob/858679423cc4778f9961d4aaf3c061a9368985ec/document-release/sections/release-body.md)

**Implication for BStack.** An executable check can establish that an implementation follows a rule. A source-linked topic can still explain where the rule came from, when it applies, and which decision it changes. A provider’s documented contract, the origin of an SLA, the meaning of a domain term, or the procedure for recovering a deployment can remain useful after the code that first introduced it changes. Preserve those facts where readers look for them and put implementation enforcement at the surface where the rule matters.

## BStack guidance

The guidance lives in the [Comments and documentation](../skills/burbi-mode/references/comments-and-documentation.md) reference, which moved out of `SKILL.md` on 2026-11-20 ([why](workflow-organization.md#router-prose-moved-to-rows-and-references)). It applies alongside the project’s own documentation workflow. The same change can need both a check and a durable explanation. For example, a provider may require a delay before retrying. A check can exercise the implementation. A provider topic can identify the contract, which environments it covers, and where the next maintainer should confirm it. A short comment can point to that context at a surprising branch.

If a comment describes a workaround in the project’s own design, trace the constraint that made it necessary. Fix or constrain the behavior when that is in scope. A workaround that must remain needs a real reason and a condition that would let it be removed, when known. A second summary of an ordinary refactor earns a page only if it meets a reader need or an existing project requirement. The review question is what a maintainer will know or do differently after reading the prose.

## Fixture checks

With Pi and DeepSeek V4.1 Flash, a disposable provider-policy change updated the polling behavior, the owning topic, and the required changelog. The approved notice and license line survived. An independent CLI run confirmed the intended sandbox delay and existing production delay. A read-only Review reported the mismatch between the approved notice and the observed sandbox delay. With the approved notice deliberately absent, Review reported both the measured delay and the missing authority. Both reviews preserved the fixture. Refactor kept the provider rationale, removed a redundant comment, and kept the edits in the code. The independent CLI check passed.

The first prompt for the policy change was ambiguous about whether it was a defect or an intentional change. Pi chose Bug fix, performed the correct edits, and passed the CLI check. The final prompt specified Feature. On the previous revision, one Refactor run opened project files before its playbook. The same prompt opened Refactor first on a fresh repeat. All four final runs opened their selected playbook first. The final refactor trace included an edit call aimed at the BStack directory outside the fixture. The BStack working-tree file list and skill hash matched the intended edits after the run. These trials exercise documentation behavior on a synthetic repo.
